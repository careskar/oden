1. Sammanfattning

Odens grundval håller. Alla fyra projekten landar i samma lösning som planen: hooks för status i realtid, agentens egna transkript för tokens och historik, och en lokal daemon som normaliserar till ett eget format. Ingen av dem använder en API-proxy. Ingen av dem förlitar sig på OpenTelemetry för användardata.

Det som skiljer dem från Oden är att de äger sessionen. herdr och Orca äger terminalen som agenten kör i, och T3 Code och Paseo startar agenten själva via Agent SDK eller app-server-protokoll. Oden ska bara observera sessioner som startas var som helst. Det gör Oden enklare, men vi går miste om två signaler de har: skärmen och tangentbordet.

De viktigaste lärdomarna för Oden:

  1. Fler hook-events behövs, och några betyder något annat än man tror. StopFailure, PostCompact, Elicitation, TeammateIdle och Notification med idle_prompt saknas i planen. PreCompact kan komma även när komprimeringen avbryts, och Stop kommer inte alls när du avbryter en tur.
  2. Tokens från transkriptet räknas lätt dubbelt. Claude Code skriver en rad per innehållsblock, och varje rad upprepar hela usage-objektet. T3 Code mätte en överräkning på ungefär 2,4 gånger. Lösningen är att deduplicera på message.id + requestId.
  3. Statusraden ger 5-timmars- och veckogränserna (rate_limits) för prenumerationskonton. Orca läser dem därifrån, med strypning, i stället för att fråga ett API.
  4. Insamlaren ska tåla att daemonen startas om på ny port. Orca låter hook-skriptet läsa en endpoint-fil vid varje anrop, så att långlivade sessioner hittar rätt även efter omstart.
  5. ”Klar tills du har sett den” är ett eget tillstånd i alla fyra. Det är den mest användbara inkorgssignalen och den saknas i Odens statusmaskin.
  6. Kostnad kan räknas lokalt redan i fas 2 med LiteLLM:s öppna prislista plus egna överstyrningar, precis som T3 Code gör. OpenTelemetry behövs inte för det.

3. herdr

Så samlar herdr in data

Skärmdetektion huvudkälla

herdr läser de nedersta raderna i varje panels terminalbuffert och matchar dem mot ett TOML-manifest per agent (src/detect/manifests/claude.toml m.fl., 22 agenter). Reglerna har prioritet, region (t.ex. bottom_non_empty_lines(12) eller osc_title) och AND/OR/NOT-villkor. Exempel: Claudes spinner i fönstertiteln betyder working, och ”Do you want to proceed?” betyder blocked.

Manifesten uppdateras från herdr.dev utan ny release. Lokala överstyrningar i ~/.config/herdr/agent-detection/ vinner alltid.

Hooks identitet

Claude-integrationen lyssnar bara på SessionStart och skickar session_id, transcript_path och source till herdrs Unix-socket. Det används för att kunna återuppta sessionen med claude --resume efter omstart, inte för status. Subagenter (agent_id satt) och Cursor (som importerar Claudes hooks) filtreras bort.

Rapport-API för agenter

Agenter som vill kan själva rapportera idle/working/blocked med herdr pane report-agent. Varje rapport har ett --seq som måste öka; äldre eller sena rapporter ignoreras. Rapporter vinner över skärmdetektionen så länge de kommer.

Events och väntan

Socket-API:t har events.subscribe med filter (t.ex. bara blocked). Historiken är inte beständig: halkar en prenumerant efter får den events_lost och ska läsa en ny ögonblicksbild. herdr agent wait --until blocked|done låter skript vänta på en agents tillstånd.

Värt att notera

  • Strikt ”blocked”. herdr markerar bara blocked när en känd dialog syns. Annars blir det idle, med motiveringen att automatik som litar på fel status kan skriva in i en godkännandedialog.
  • herdr agent explain visar vilken regel som matchade, vilken manifestversion som användes och varför. Ett bra mönster för Oden: förklara härledd status utifrån vilka events som kom.
  • Rollup: en blockerad agent gör hela fliken och arbetsytan blockerad. En klar agent förblir ”done” tills du tittat på den.
  • Integrationer versioneras. Skripten innehåller HERDR_INTEGRATION_VERSION=11, och herdr integration status visar vad som är installerat. Avinstallation tar bara bort herdrs egna rader.

4. T3 Code

Så samlar T3 Code in data

Egen orkestrering huvudkälla

T3 Code startar agenten och tar emot dess ström. Varje provider har en adapter som översätter till egna events. Modellen är en graf: Project → AppThread → Run → ExecutionNode, plus ProviderThread och ProviderSession för agentens egna id:n.

Bara de normaliserade eventen är beständiga. Rådata från providern sparas för felsökning, men den bär inte appens tillstånd.

Sekvens och ögonblicksbild

Varje lagrat event får ett ökande sequence av lagret. Klienter läser en ögonblicksbild vid sekvens N och strömmar sedan allt med sekvens > N. Det ger korrekt återanslutning utan dubbletter.

Usage från transkript direkt användbart

Usage-vyn läser agenternas egna sessionsfiler, oavsett om T3 startade dem: ~/.claude/projects (eller CLAUDE_CONFIG_DIR), ~/.codex/sessions, OpenCodes SQLite m.fl. Filerna cachas på storlek och mtime så att bara ändrade filer läses om.

Priser hämtas från LiteLLM:s model_prices_and_context_window.json. Man kan ange egna priser per modell och mappa en modell till en annan (”räkna preview-modellen som den släppta”). Kostnaden kallas uttryckligen ”API-ekvivalent”, inte din faktura.

Gränser och konton

5-timmars- och veckogränser hämtas via Agent SDK:s usage-anrop och Anthropics OAuth-usage-endpoint med den inloggning Claude Code redan har. Flera konton på flera maskiner slås ihop och räknas en gång.

Detaljer från Claude-parsern

apps/server/src/provider/Drivers/claudeUsage.ts är den mest konkreta lärdomen för Odens berikare:

  • Bara rader med type: "assistant" och message.usage räknas.
  • Modellen <synthetic> är lokala platshållare som aldrig nådde API:t och hoppas över.
  • Deduplicering på message.id + requestId. Utan den räknas ungefär 2,4 gånger för mycket.
  • usage.iterations med typ advisor_message är anrop till en annan modell och blir egna rader med den modellens pris.
  • usage.speed === "fast" har annat pris. costUSD används om den finns.
  • Tänkande tokens ingår i output_tokens och kan inte särskiljas.

För att läsa hela konversationer (t.ex. vid import) använder T3 Code Agent SDK:s getSessionMessages i stället för att tolka JSONL själv. Det är ett stabilare kontrakt än det interna filformatet.

Värt att notera

  • Agenter utanför T3 kan ansluta via en MCP-server (OAuth, läs-endast som standard) och läsa trådar och starta nya. Samma verktyg finns som t3 thread start/send --wait på värden.
  • Mobilnotiser när en agent blir klar, misslyckas, behöver godkännande eller ställer en fråga, plus Live Activities på iOS och en hemskärmswidget med kvarvarande kvot.
  • Telemetri skickar provider, modell, tider och tokens med hashade id:n, aldrig prompter eller svar. Ett bra mönster om Oden någonsin synkar till en hostad tjänst.

5. Orca

Orca har det mest genomarbetade hook-systemet av de fyra, och det ligger närmast det Oden ska bygga. Allt i src/main/agent-hooks/ och src/main/claude/ är värt att läsa.

Två kanaler

Managed hooks som Oden

Orca installerar ett skript per agent som POSTar event-JSON till en hook-server på 127.0.0.1. Varje terminal får ORCA_AGENT_HOOK_PORT, ORCA_AGENT_HOOK_TOKEN och ORCA_PANE_KEY. Saknas de, eller misslyckas POST:en, skrivs eventet till en lokal spool. Samma upplägg som Odens korp.

Hooks ger: status, prompt, verktyg och indata, agentens svar, sessions-id, modell och subagenter.

OSC 7501 ny källa

Program Status Protocol: agenten skriver sin egen status som en escape-sekvens i terminalströmmen (ESC ] 7501 ; …), med tillstånden idle/working/done/blocked/error, orsaken (permission, question, auth), en meddelanderad och barnposter för subagenter.

Claude Code skickar det sedan 2.1.295, men bara om terminalen svarar på en förfrågan. Det saknar prompt och sessions-id, så Orca använder det bara som reserv när hooks är tysta.

Robusthet i insamlaren

  • Endpoint-fil. Porten och token skrivs till {userData}/agent-hooks/endpoint.env, och skriptet läser in filen vid varje anrop. En session som startades före en omstart av Orca hittar då ändå rätt.
  • Miljövariabler kan försvinna. CLAUDE_CODE_SUBPROCESS_ENV_SCRUB rensar miljön för hook-processer, så Orca återställer sina variabler innan skriptet läser dem.
  • Alltid giltig stdout. Skriptet skriver {} först, eftersom Orca observerat att tillståndshooks kan ”stänga” (neka) när stdout är tom. Värt att verifiera i Odens PoC.
  • Dubbla events från andra harnesses. Cursor, Devin, Grok och Qoder importerar Claudes hooks. Orca hoppar över eventet när t.ex. DEVIN_PROJECT_DIR är satt, så att det inte räknas som en Claude-session.
  • Hook-data via stdin/fil, aldrig på kommandoraden. Undviker storleksgränser och att innehållet syns i processlistor.
  • Versionsstyrd installation. Vilka events som installeras beror på Claude Codes version. SessionEnd installeras först från 2.1.261, eftersom leveransen var opålitlig före det.

Statusraden

Orca installerar ett statusrads-skript som skickar statusradens JSON vidare, men bara när den innehåller rate_limits (prenumerationskonton) och högst en gång per intervall. Det ger 5-timmars- och veckogränser utan att fråga något API. Skriptet skriver ingenting själv, så användarens egen statusrad påverkas inte.

Historik, sök och statistik

  • AI Vault / Agent Session History skannar alla agenters sessionsfiler på disk och listar dem med titel, katalog, branch, modell, första prompt och senaste turer. Man kan söka (ett eget SQLite-index i ai-vault-search/), filtrera på arbetsyta/projekt/allt, och återuppta med rätt kommando (claude --resume <id>, codex resume <id> …) eller kopiera kommandot.
  • Agent Dashboard är en kanban med kolumnerna Needs You, Working, Done och Idle (inget hänt på ca 30 min). Korten visar senaste meddelandet och den väntande frågan.
  • Statistiken är tunn: antal agenter, total agenttid och antal PR:er. Oden siktar betydligt högre.
  • Usage hämtas från api.anthropic.com/api/oauth/usage med Claude Codes inloggning, ungefär var 15:e minut när fönstret är aktivt, med varning vid 80 %.

Hook som fattar beslut

Orca låter plugins svara på PreToolUse: skriptet väntar högst 8 sekunder, Orca svarar inom 6, och vid timeout eller fel skrivs {} så att anropet fortsätter som om Orca inte fanns. Det är en konkret mall för idén ”Policy via hooks” i Odens plan.

6. Paseo

Så samlar Paseo in data

Egna agenter

Daemonen startar Claude via Agent SDK, Codex via app-server och andra via ACP eller RPC. Varje provider implementerar samma AgentClient-gränssnitt och normaliserar verktygsanrop till en gemensam typ (shell, read, edit, write, search …). Providerns egen historik (t.ex. ~/.claude/projects/…jsonl) är sanningskällan när en session återupptas.

Terminal-agenter via hooks

Terminaler får PASEO_TERMINAL_ID, PASEO_ACTIVITY_TOKEN, PASEO_TERMINAL_ACTIVITY_URL och PASEO_HOOK_CLI. Hooken kör paseo hooks claude <event>, som översätter till ett grovt tillstånd och POSTar det. Saknas något blir det en no-op.

Claude-mappningen och avbrott

Claude-eventPaseos tillstånd
UserPromptSubmitrunning
Stop, StopFailure, SessionEndidle
Notification med notification_type = idle_promptneeds-input

Claude kör inte Stop när du avbryter en tur. Paseo ser Ctrl-C och Escape i terminalen och nollställer då statusen. Oden ser inte tangentbordet, men transkriptet får raden [Request interrupted by user] (Orca läser den) och nästa UserPromptSubmit avslutar ändå den gamla turen. Oden behöver hantera detta, annars fastnar sessionen i working.

Uppmärksamhet och notiser

  • Attention är ett eget fält: när något går från arbetar till klar sätts ”finished”, och det ligger kvar tills du läser chatten. Det skiljer ”klar och oläst” från ”klar och sedd”.
  • Närvarostyrda notiser (agent-attention-policy.ts): klienterna skickar heartbeat med synlighet, fokuserad agent och senaste aktivitet. Tittar du redan på agenten skickas ingen notis. Har du varit aktiv i en klient de senaste 3 minuterna visas notisen där. Annars går den som push till mobilen. Fel ger ingen push.
  • Live-ström + auktoritativ historik: klienten får deltan i realtid men kan alltid hämta hela tidslinjen sidvis och upptäcka luckor via sekvensnummer. Varje post har ett storlekstak (64 KiB för verktyg, 256 KiB annars) med en tydlig trunkeringsmarkör.

Övrigt

  • Usage för Claude, Codex, Copilot m.fl. ligger i separata plugins (plugins/claude-usage-source), som läser OAuth-token från ~/.claude/.credentials.json eller nyckelringen.
  • All lagring är JSON-filer under ~/.paseo med atomära skrivningar och Zod-scheman, utan migreringar.
  • Inga telemetridata alls, uttalat som en princip.

10. Sådant vi inte bör kopiera

  • Att starta agenterna själv (T3 Code, Paseo). Det ger rikare data men låser in användaren i Odens gränssnitt. Odens styrka är att det fungerar med sessioner som startas var som helst.
  • Skärmdetektion (herdr). Kräver att man äger terminalen och ett ständigt underhåll av regex per agentversion. herdr har ett helt uppdateringssystem bara för det.
  • Odokumenterade API-anrop som standard. Orca, T3 Code och Paseo använder /api/oauth/usage med Claude Codes token. Det fungerar men är inget publikt kontrakt och hanterar dina inloggningsuppgifter. Statusraden räcker för gränserna. Erbjud endpointen högst som opt-in.
  • Telemetri till tredje part (T3 Code → PostHog). Krockar med Odens local-first-princip. Paseos ”ingen telemetri” passar Oden bättre.
  • Orcas komplexitet i statusreglerna. Den finns av goda skäl, men Oden har en fördel: allt sparas som rådata, så reglerna kan förbättras i efterhand och köras om. Börja enkelt och lägg till fall när loggen visar dem.

11. Ändringar i Odens plan

Fas 0 – PoC

  • Registrera även StopFailure, PostCompact, Elicitation, ElicitationResult, TeammateIdle och Notification.
  • Korpen läser port och token från ~/.oden/endpoint vid varje anrop, och sätter harness utifrån miljön så att Cursor, Devin m.fl. inte räknas som Claude Code.
  • Verifiera vad tom stdout gör för PermissionRequest/PreToolUse. Skriv {} om det behövs.
  • Testa avbrott (Esc) och /compact och se vilka events som faktiskt kommer.
  • Transkriptskriptet deduplicerar på message.id + requestId, hoppar över <synthetic> och räknar advisor_message-iterationer separat.

Fas 1 – MVP

  • Statusmaskinen får tillstånden done_unseen och underläget ”bakgrundsarbete pågår”. Subagent-events (agent_id) hålls isär från huvudsessionen.
  • Statusrads-korpen skickar rate_limits och kontextfyllnad, strypt till t.ex. en gång per 30 s.
  • Kanban-vy, oden explain, oden wait och närvarostyrda notiser.
  • Varje lagrat event får en sekvens från SQLite. Live-strömmen (SSE) använder den som markör, så att dashboarden kan återansluta utan luckor.
  • oden integration install|status|uninstall med version i skriptet. Avinstallation tar bara bort Odens egna rader.

Fas 2 – Statistik

  • Import av historik med inkrementell läsning (cache på storlek och mtime), plus sessionslista med resume-kommando.
  • Kostnad från LiteLLM:s prislista med egna priser och modellmappning. Flyttas hit från fas 3.
  • Överväg Agent SDK:s getSessionMessages för att läsa hela konversationer i stället för att tolka JSONL direkt.

Fas 3–5

  • OpenTelemetry blir valfritt: för den som redan har Grafana eller vill ha exakt kostnad, inte en förutsättning.

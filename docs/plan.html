Oden · Plan för issue #1

Ett kontrolltorn för AI-agenter och prompter

Ett system som tar emot händelser från alla agent-sessioner (Claude Code, Claude Cowork och andra harnesses), visar live-status för varje session och bygger upp statistik över hur du jobbar med dina agenter.

Namnet passar: Oden hade korparna Hugin och Munin som flög ut i världen och rapporterade tillbaka. Här är korparna små insamlare som sitter i varje session.

1. Mål och krav

Live-översikt

Vilka sessioner pågår just nu, på vilken maskin och i vilket repo? Jobbar agenten, väntar den på mig, behöver den ett tillstånd, eller har den fastnat? Hur full är kontexten?

Statistik över tid

Promptlängd, modellval, hur länge agenten jobbar per tur, hur ofta och hur snabbt jag svarar, verktygsanvändning, tokens och kostnad, komprimeringar.

Promptarkiv

Alla prompter jag skickat, sökbara, kopplade till sessionen och utfallet. Senare även ett bibliotek med prompter jag återanvänder.

Fungerar med flera harnesses

Claude Code och Claude Cowork först. Andra agenter (Codex CLI, Gemini CLI, Cursor, egna Agent SDK-agenter) via adaptrar till ett gemensamt händelseformat.

2. Rekommendation i korthet

Använd hooks för status och flera kompletterande källor för siffrorna. Hooks är det enda sättet att få exakta tillståndsövergångar i realtid: när en tur börjar och slutar, när agenten väntar på tillstånd, när den går idle. Men hooks får inte med tokens, kostnad eller kontextfyllnad. Det hämtar vi från sessionens transkript (JSONL), från statusraden och, i ett senare steg, från Claude Codes inbyggda OpenTelemetry-export.

  1. Insamlare (”korpar”): ett litet hook-skript eller en HTTP-hook som skickar varje händelse vidare, utan att blockera sessionen.
  2. Ingest-tjänst: en lokal daemon som tar emot händelser, normaliserar dem och sparar dem i en append-only-logg (SQLite).
  3. Processor: kör en statusmaskin per session och räknar fram turer, tider och aggregat.
  4. Dashboard: live-vy via WebSocket eller SSE plus statistikvyer. Dessutom notiser när en session väntar på dig.

Allt körs lokalt först (local-first, inga prompter lämnar datorn). Moln-sessioner, som Claude Code on the web, når inte localhost. För dem behövs i en senare fas en hostad ingest-endpoint eller en relay.

3. Datakällor: hooks och alternativ

Hooks är en bra grund, men inte det enda alternativet. Här jämförs de vägar som finns, med fördelar och nackdelar.

A. Command-hooks Kärna

Ett skript som körs vid varje hook-event och får event-JSON på stdin.

  • Exakta statusövergångar i realtid
  • Fungerar även när daemonen är nere (skriv till lokal kö-fil)
  • Kan paketeras som plugin och installeras med ett kommando
  • En process startas per event, vilket ger latens om det görs synkront
  • Ingen token-, kostnads- eller kontextdata
  • Varje harness har sitt eget hook-format

B. HTTP-hooks Kärna, MVP

Hooken POSTar event-JSON direkt till en URL i stället för att starta ett skript.

  • Ingen processstart, så lägre overhead
  • Enkel konfiguration, ingen kod hos klienten
  • Fungerar mot en hostad endpoint för moln-sessioner
  • Händelser försvinner om mottagaren är nere (ingen lokal buffring)
  • Fortfarande ingen token- eller kontextdata

C. Transkript (JSONL) Komplement

Varje hook får transcript_path. Filen innehåller alla meddelanden med modell och usage (tokens).

  • Ger kontextfyllnad, tokens och modell per tur
  • Historik kan importeras i efterhand, även för gamla sessioner
  • Internt format som kan ändras mellan versioner
  • Finns bara på maskinen där sessionen körs

D. Statusrad Komplement

Claude Codes statusline-skript får sessionsdata, inklusive kontextfönstrets användning, och körs ofta.

  • Färdigberäknad kontextfyllnad, nästan i realtid
  • Du ser samtidigt Oden-status i terminalen
  • Bara i den interaktiva terminalen, inte i headless-läge eller moln
  • Användaren har bara en statusrad, så den kan krocka med en befintlig

E. OpenTelemetry Fas 3

Claude Code kan exportera metrics och events via OTLP: tokens, kostnad, API-anrop, verktygsbeslut, promptevents (prompttext bara om man slår på det).

  • Officiellt och stabilt kontrakt, rik data om tokens och kostnad
  • Standardformat som även andra harnesses (t.ex. Codex, Gemini CLI) har stöd för
  • Kan skickas till Grafana, Honeycomb m.fl. parallellt
  • Batchad export, så inte omedelbar
  • Saknar tillstånd som ”väntar på dig”
  • Mer att sätta upp: en OTLP-mottagare behövs

F. API-proxy Avråds

Peka ANTHROPIC_BASE_URL mot en proxy (t.ex. LiteLLM) som loggar varje anrop.

  • Helt harness-oberoende, ser exakt varje modellanrop
  • Ligger i den kritiska vägen: om proxyn går ner slutar agenterna fungera
  • Krånglig autentisering, fungerar dåligt med prenumerationsinloggning
  • Ser inte UI-tillstånd (väntar, tillstånd, idle)

4. Hooks att koppla in sig på (Claude Code)

Alla hook-events får gemensamma fält: session_id, transcript_path, cwd, permission_mode och hook_event_name. Därtill kommer event-specifika fält. Listan bygger på dokumentationen i skrivande stund. Nya events tillkommer, så insamlaren ska skicka vidare alla events oförändrade och låta servern avgöra vad som är intressant.

Exempel: hook-konfiguration för PoC

Samma skript registreras för alla events. Det ska alltid avslutas med kod 0 och aldrig blockera agenten.

// ~/.claude/settings.json (utdrag)
{
  "hooks": {
    "SessionStart":     [{ "hooks": [{ "type": "command", "command": "~/.oden/bin/raven" }] }],
    "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "~/.oden/bin/raven" }] }],
    "PreToolUse":       [{ "matcher": "*", "hooks": [{ "type": "command", "command": "~/.oden/bin/raven" }] }],
    "PostToolUse":      [{ "matcher": "*", "hooks": [{ "type": "command", "command": "~/.oden/bin/raven" }] }],
    "Stop":             [{ "hooks": [{ "type": "command", "command": "~/.oden/bin/raven" }] }],
    "SessionEnd":       [{ "hooks": [{ "type": "command", "command": "~/.oden/bin/raven" }] }]
    // … samt PermissionRequest, Notification, PreCompact, Subagent*
  }
}
#!/usr/bin/env bash
# ~/.oden/bin/raven – lägger till metadata och skickar vidare utan att blockera
payload=$(cat)
event=$(jq -c --arg host "$(hostname)" --arg h "claude-code" \
  '{received_at: (now|todate), harness: $h, host: $host, raw: .}' <<<"$payload")
echo "$event" >> ~/.oden/spool.jsonl                     # lokal buffert, tål att servern är nere
curl -s -m 1 -X POST localhost:4747/ingest -d "$event" >/dev/null 2>&1 &
exit 0

Prestanda: hooks körs i sessionens kritiska väg. Insamlaren måste vara snabb (under ~50 ms), ha kort timeout och skicka i bakgrunden. Tunga saker som transkript-parsning görs på serversidan, aldrig i hooken.

6. Processflöde

Varför event sourcing? Rådata sparas oförändrad och allt annat härleds ur den. När vi kommer på ett nytt mätvärde, eller hittar ett fel i statusmaskinen, kör vi om hela loggen och får korrekt historik. Det är billigt i SQLite och sparar mycket huvudvärk.

7. Statusmaskin för sessioner

  • working: med detaljer om aktuellt verktyg (från PreToolUse) och om subagenter kör.
  • waiting_permission: agenten är blockerad tills du svarar. Högst prioritet i inkorgen.
  • waiting_input: turen är klar och agenten väntar på nästa prompt. Tiden här är din ”reaktionstid”.
  • stale: inga events på länge (krasch, stängd terminal utan SessionEnd, eller fastnat).

9. Statistik och mätvärden

Hur jag promptar

  • Promptlängd (tecken/ord), fördelning och trend
  • Prompter per session, uppföljningar kontra nya uppgifter
  • Andel korrigerande prompter (”nej, inte så”, avbrutna turer)
  • Tid på dygnet och veckodag

Hur agenterna jobbar

  • Agenttid per tur (median, p90), längsta autonoma körning
  • Verktygsanvändning och felfrekvens per verktyg
  • Subagenter per session, parallella sessioner
  • Modellval per uppgiftstyp och repo

Hur mycket jag behövs

  • Manuella ingrepp per timme agentarbete
  • Tillståndsfrågor: antal, godkänd/nekad, per verktyg (underlag för bättre allowlist)
  • Min svarstid: tid i waiting_*
  • Kvot autonom tid / väntetid

Kontext och kostnad

  • Kontextfyllnad över sessionens livstid
  • Komprimeringar per session, fyllnad vid komprimering
  • Tokens in/ut, cache-träffar, kostnad per session, repo och dag
  • Kostnad per avslutad uppgift (kopplat till commit/PR)

11. Integritet och säkerhet

  • Local-first: daemonen lyssnar bara på 127.0.0.1. Inga prompter lämnar maskinen förrän du själv slår på synk eller hostad ingest.
  • Prompttext är opt-in per källa: lagra bara längd och hash som standard. Hela texten sparas där du uttryckligen slår på det.
  • Maskering: filtrera bort hemligheter (API-nycklar, tokens, .env-innehåll) i tool_input/tool_response innan lagring.
  • Autentisering: token per maskin/harness för ingest, så att en läckt token kan återkallas separat.
  • Hooks får aldrig påverka agenten: korpen returnerar alltid 0 och skriver inget till stdout, så att den aldrig blockerar eller ändrar beteendet.

12. Faser: PoC → MVP → vidare

Fas 0 – Proof of concept

Mål: bevisa att vi kan få korrekt live-status och grundstatistik från Claude Code, och ta reda på vad som går i Cowork. Omfattning: några dagar.

  • Korp-skript (bash + jq + curl) registrerat för alla hook-events, skriver till ~/.oden/spool.jsonl
  • Logga några dagars riktiga sessioner och granska vilka fält som faktiskt kommer
  • Liten oden ls-CLI som läser spool-filen och visar sessioner med härledd status
  • Skript som läser transkript och räknar ut kontextfyllnad och tokens per tur
  • Testa Cowork: laddas hooks/plugins? Var ligger sessionsdata?
  • Mät korpens latens. Mål under 50 ms per event

Klart när: oden ls visar korrekt status för 3+ parallella Claude Code-sessioner, och vi vet hur Cowork ska kopplas in.

Fas 1 – MVP

Mål: något du använder varje dag. Omfattning: 1–2 veckor.

  • Oden-daemon (TypeScript) med POST /ingest, SQLite-händelselogg och statusmaskin
  • Byt till HTTP-hooks där det går, behåll spool-reserven och ladda upp spool vid omstart
  • Berikare för transkript: modell, tokens, kontext-%
  • Dashboard: live-lista, ”väntar på dig”-inkorg, sessionsdetalj med tidslinje
  • Promptarkiv med fritextsök
  • Desktop-notis när en session väntat på tillstånd längre än X sekunder
  • Paketera som Claude Code-plugin: installation med ett kommando
  • Cowork-adapter enligt resultatet från PoC

Klart när: du kan lämna terminalen och ändå veta vilken session som behöver dig, och se dagens statistik.

Fas 2 – Statistik och insikter

Omfattning: 1–2 veckor.

  • Statistikvyer: promptlängd, agenttid, väntetid, ingrepp, verktyg, modeller
  • Aggregattabeller och filtrering på period, repo, harness och modell
  • Import av historiska transkript (~/.claude/projects)
  • Veckorapport (HTML/mejl): ”så här jobbade du med agenter i veckan”
  • Förslag på allowlist utifrån vilka tillståndsfrågor du alltid godkänner

Fas 3 – OpenTelemetry och kostnad

Omfattning: ca 1 vecka.

  • OTLP-mottagare i daemonen (/v1/metrics, /v1/logs)
  • Korrelera OTel-data med hook-sessioner via session-id
  • Kostnad per session, repo och dag, med budgetlarm
  • Valfri vidarebefordran till Grafana eller liknande

Fas 4 – Fler harnesses, fler maskiner och moln

Omfattning: löpande.

  • Hostad ingest (t.ex. liten server med Postgres) med tokens per maskin
  • Repo-baserade hooks så att Claude Code on the web och andra moln-sessioner rapporterar in
  • Adaptrar för Codex CLI, Gemini CLI, Cursor och egna Agent SDK-agenter
  • Synk mellan lokal daemon och hostad instans

Fas 5 – Utbyggnad
